Overview

무엇을 만들었나

플레이어는 꿈의 미로에 갇혀 있습니다. 흩어진 열쇠 5개를 모으면 미로 끝에 Goal Point가 생성되고, 그곳에 도달하면 탈출합니다. 미로를 배회하는 몬스터에게 3회 피격되거나, Arcane 레이어에 오래 머물러 정신력이 바닥나면 게임 오버입니다.

기본 레이어. 차갑고 어두운 조명 아래에서 정신력이 회복됩니다. 몬스터는 시야각과 벽 차폐를 모두 통과해야만 플레이어를 감지합니다.

ARCANE

01
상태는 FSM으로

몬스터 AI와 게임 흐름을 각각 interface 기반 State 패턴으로 분리했습니다. 조건 분기가 아니라 상태 객체가 자기 행동과 전환 조건을 소유하므로, 상태를 추가해도 컨트롤러를 건드릴 일이 없습니다.

02
규칙은 MonoBehaviour 밖으로

클리어 / 게임오버 판정은 GameRule이라는 순수 C# 클래스가 담당합니다. 씬과 유니티 생명주기에 묶이지 않으므로 그대로 테스트할 수 있습니다.

03
생성 / 파괴 대신 재사용

벽 · 몬스터 · 열쇠 모두 ObjectPool<T> 기반입니다. 재시작해도 Instantiate / Destroy가 발생하지 않습니다. 대신 재사용 시점의 상태 초기화를 각 컴포넌트가 명시적으로 책임집니다.

Core Implementation

핵심 구현

전체 64개 파일 중, 설계 판단이 실제로 드러나는 여섯 곳을 골랐습니다.

01

절차적 미로 생성 — 반복 DFS

그리드의 모든 셀을 벽으로 채운 뒤, 깊이 우선 탐색으로 지나간 경로의 벽만 허무는 방식입니다. 셀 수가 늘면 재귀는 스택 오버플로우 위험이 있어 명시적 Stack<Cell>을 사용한 반복 구현을 선택했고, 시드를 주입할 수 있게 해 두 레이어가 서로 다른 미로를 갖도록 했습니다.

할당 제거 GetUnvisitedNeighbors()는 셀 수만큼 호출됩니다. 매번 새 List를 만들면 20×20 미로 하나에 400회 이상의 힙 할당이 생기므로, 필드에 캐시 리스트를 두고 Clear() 후 재사용하도록 했습니다.
02

이중 레이어 전환 — 이 프로젝트의 중심

두 개의 MazeGenerator와 두 개의 NavMeshSurface를 동시에 들고 있다가 활성 레이어에 맞춰 스왑합니다. 비활성 레이어의 벽은 파괴하지 않고 Renderer.enabled = false + Collider.isTrigger = true로 남겨둡니다. 재생성 비용이 없고, 무엇보다 "지금은 통과할 수 있지만 전환하면 벽이 되는 위치"를 물리적으로 검사할 수 있게 됩니다.

두 미로는 벽 배치가 다르므로, 그냥 전환하면 플레이어가 벽 속에 갇힙니다. 전환을 실행하기 전에 Physics.CheckSphere로 전환할 레이어의 벽 마스크와 겹치는지 먼저 검사해 원천 차단했습니다.

03

몬스터 AI — interface 기반 FSM

IMonsterState를 구현한 Idle / Chase / Attack 세 상태가 각자 자신의 행동과 전환 조건을 소유합니다. MonsterController는 컴포넌트 조합과 Tick 위임만 담당합니다.

일반적인 FSM은 Tick() 안에서 상태가 바뀌면 새 상태의 첫 행동이 다음 프레임으로 밀립니다. 추격 → 공격 전환에서 한 프레임 멈칫하는 문제가 있어, 상태가 바뀌면 같은 프레임에 새 상태까지 이어서 실행하되 safety 카운터로 무한 루프를 차단했습니다.

04

시야 판정 — 값싼 검사부터 순서대로

몬스터 10마리가 매 FixedUpdate마다 시야를 검사하므로, 연산 비용이 낮은 조건부터 걸러내는 순서를 설계했습니다. Acos를 쓰지 않기 위해 cos(FOV/2)를 Awake에서 미리 계산해두고, 매 프레임은 내적 1회 비교로 각도 판정을 끝냅니다.

판정 순서 거리 (sqrMagnitude 비교 · sqrt 없음) → 각도 (내적 1회 · Acos 없음) → 차폐 (Raycast 1회). 가장 비싼 Raycast는 앞의 두 조건을 모두 통과했을 때만 실행됩니다.
05

게임 시작 연출 — Awaitable 시퀀스와 복구 보장

미로 생성 → 유닛 스폰 → 인트로 카메라 → 등장 애니메이션 → 팔로우 카메라 블렌드까지를 코루틴이 아닌 Unity 6의 Awaitable로 순차 제어했습니다.

가장 신경 쓴 부분은 finally 복구입니다. 연출 중 예외가 나거나 오브젝트 파괴로 취소되면 Time.timeScale이 0, 입력이 차단된 채로 영영 남을 수 있습니다. 어떤 경로로 빠져나가도 반드시 정상 상태로 돌아오게 했습니다.

애니메이션 종료는 길이를 하드코딩한 WaitForSeconds 대신 Animator의 실제 상태 전이를 폴링해, 트랜지션 블렌드까지 포함한 정확한 시점을 잡았습니다.

06

입력 — 단일 게이트로 통합

초기에는 매 프레임 Keyboard.current를 직접 폴링했습니다. PlayerInput의 onActionTriggered 콜백 기반으로 바꾸면서 바인딩은 에셋으로 분리하고, 차단은 IsControlEnabled 프로퍼티 하나로 통합했습니다. Pause · Result · 인트로 연출 · 레이어 전환 연출 중의 입력 차단이 여러 곳에 흩어지지 않게 하기 위한 단일 게이트입니다.

Troubleshooting

증상에서 원인까지

가장 오래 붙잡았던 세 가지입니다. 두 개는 증상이 같았지만 원인이 전혀 달랐습니다.

01

몬스터가 벽을 통과한다 ① — NavMesh에 뚫린 구멍

증상재시작을 몇 번 반복하면 일부 몬스터가 특정 벽 구간을 그대로 통과해 지나감
원인벽은 ObjectPool로 재사용되는데, 비활성 레이어에 있던 벽은 isTrigger = true 상태로 반납됨. NavMesh Bake는 트리거 콜라이더를 장애물로 인식하지 않으므로, 그 상태로 재사용된 벽 위치에 NavMesh가 그대로 깔려 통로가 뚫림
해결풀에서 꺼낸 직후, Bake 이전에 렌더러 / 콜라이더를 솔리드 상태로 강제 리셋
배운 점 오브젝트 풀은 이전 사용 이력을 그대로 안고 돌아옵니다. 재사용 시점의 상태 초기화를 빠뜨리면, 그 오브젝트를 소비하는 다른 시스템(NavMesh Bake)에서 전혀 다른 증상으로 터집니다. 이후 몬스터(ResetForReuse) · 공격 트리거(ResetTrigger) · FSM(ResetState)에도 동일하게 명시적 리셋 메소드를 두는 규칙으로 정리했습니다.
02

몬스터가 벽을 통과한다 ② — Agent가 이전 NavMesh에 남음

증상Tab으로 레이어를 전환한 직후, 이동 중이던 몬스터가 새 미로의 벽을 뚫고 이동
원인두 미로는 벽 배치가 달라 몬스터가 서 있던 자리가 새 레이어에서는 벽 내부일 수 있음. NavMeshAgent가 이전 레이어의 NavMesh 위에 올라간 상태와 경로를 유지한 채 계속 이동함
해결OnLayerChanged를 구독해, 전환 직후 제자리에 Warp()를 다시 걸어 새로 활성화된 NavMesh에 강제 재동기화
03

재시작해도 이전 판의 잔상이 남는다

증상Replay로 새 판을 시작해도 안개가 이전 판에서 밝혔던 영역을 기억하고, 인트로 카메라가 재생되지 않고 곧바로 팔로우 카메라로 튐
원인안개는 논리 상태를 초기화해도 화면에 그려지는 텍스처가 보간(lerp)으로 서서히 따라가기 때문. 카메라는 CinemachineBrain에 이전 판의 블렌드 상태가 남아 "이전 위치 → 인트로" 블렌드가 걸리기 때문
해결안개는 논리 초기화 + ForceUpdateFog()로 렌더링 버퍼까지 즉시 갱신. 카메라는 우선순위를 되돌린 뒤 Brain.ResetState()로 블렌드 이력 자체를 폐기
세 번째 잔상 GameRule의 이벤트를 새 판마다 다시 구독하면서 해제를 빠뜨리면, 재시작 횟수만큼 핸들러가 중복 호출되어 사운드가 겹쳐 재생됩니다. 스폰 코디네이터에서 ClearAll() / SpawnAll()을 -= / += 대칭 구조로 강제해 해결했습니다.
Optimization

매 프레임 도는 코드부터

몬스터 10마리 × 매 프레임 실행되는 경로를 기준으로, GC 할당과 반복 연산을 걷어냈습니다.

대상적용효과
미로 벽 · 몬스터 · 열쇠ObjectPool<T> 기반 생성 / 반납재시작 시 Instantiate / Destroy 없음 (벽만 800개 규모)
벽 컴포넌트 접근WallEntry struct에 Renderer / Collider 참조 캐싱레이어 전환마다 발생하던 GetComponent 수백 회 제거
시야각 판정cos(FOV/2) 사전 계산 + 내적 비교Acos 호출 제거 — 매 프레임 삼각함수 연산 없음
거리 판정sqrMagnitude 비교sqrt 연산 제거
몬스터 시야 메시MarkDynamic + 배열 재사용 + 0.05초 주기 갱신 + 개체별 랜덤 시작 오프셋메시 재할당 제거, 여러 몬스터가 같은 프레임에 몰려 재계산하는 스파이크 방지
DFS 이웃 탐색필드 캐시 리스트 Clear() 후 재사용셀 개수만큼 발생하던 List 힙 할당 제거
HUD 타이머초 단위가 바뀔 때만 문자열 재생성 후 캐싱매 프레임 string 할당 → 초당 1회
애니메이터 파라미터Animator.StringToHash 사전 변환문자열 해싱 반복 제거
미로 DFS재귀 → 명시적 Stack<Cell>대형 미로에서의 스택 오버플로우 위험 제거

이 중 가장 효과가 컸던 건 시야 메시 갱신 분산입니다. 몬스터마다 90회의 Raycast로 시야 메시를 그리는데, 모두 같은 프레임에 계산하면 주기적으로 스파이크가 생깁니다. 시작 타이밍을 개체별로 어긋나게 해 부하를 프레임에 고르게 폈습니다.

Decisions

왜 이걸 골랐나

바꾼 것이 있으면 바꾼 이유가 있습니다. 네 번의 교체와 그 근거입니다.

직접 구현한 A*→NavMeshAgent + NavMeshSurface

이전 프로젝트에서 그리드 기반 A* 길찾기를 직접 구현해 이식했지만, 이 게임의 요구사항은 미로 구조가 런타임에 통째로 바뀌고 몬스터 10마리가 서로 겹치지 않게 움직이는 것이었습니다.

  • 경로 재계산 스케줄링 (10마리 × 매 프레임 재탐색 부하)
  • 에이전트 간 회피 — 몬스터끼리 겹쳐 이동하는 문제
  • 가속 / 감속 및 코너 스무딩
  • 레이어 전환 시 그래프 전체 무효화

NavMeshSurface는 런타임 Bake를 지원하고 AddData() / RemoveData()로 표면을 스왑할 수 있어 레이어 전환 요구사항과 정확히 맞았습니다. 알고리즘을 직접 구현할 수 있는지와 프로덕션에서 그걸 써야 하는지는 별개라고 판단해, 아낀 시간을 게임 고유의 문제에 투자했습니다.

코루틴→Awaitable (Unity 6)

인트로 연출은 "애니메이션 종료 대기 → 카메라 블렌드 대기" 같은 순차적 비동기 흐름입니다. 코루틴으로도 가능하지만 세 가지가 결정적이었습니다.

  • try / catch / finally가 그대로 동작 — 연출 중단 시 timeScale과 입력 차단을 되돌리는 복구 코드를 안정적으로 둘 수 있음
  • destroyCancellationToken 내장 — 파괴된 객체 접근 예외를 구조적으로 차단
  • await A(); await B(); 형태로 시퀀스를 그대로 읽을 수 있음

대기 헬퍼는 WaitScaled / WaitUnscaled로 timeScale 기준을 명시적으로 분리해, 연출 중 timeScale = 0 상황에서 의도치 않게 멈추는 실수를 방지했습니다.

UGUI→UI Toolkit + 커스텀 VisualElement

HUD와 전체 패널을 UXML + USS로 구성하고, 게임의 각진 아트 톤에 맞춰 모서리가 잘린 버튼을 커스텀 VisualElement로 직접 구현했습니다. Painter2D로 도형을 그리고, USS 커스텀 프로퍼티(--btn-fill)로 색상을 스타일시트에서 제어합니다.

schedule API를 활용해 정신력 25% 이하 시 게이지 점멸과 경고 문구 자동 숨김을 코루틴 없이 처리했습니다.

이 페이지의 버튼과 칩에 쓰인 잘린 모서리도 그 CutButton과 같은 형태입니다.

매 프레임 입력 폴링→Input System 이벤트

초기에는 Update()에서 Keyboard.current.wKey.isPressed 형태로 직접 폴링했습니다. 문제는 두 가지였습니다.

  • 키 바인딩이 코드에 하드코딩되어 변경 / 확장이 어려움
  • 입력 차단(Pause / Result / 연출 중)을 여러 곳에서 각각 처리해야 해 누락 발생

onActionTriggered 콜백으로 전환하면서 바인딩은 .inputactions 에셋으로 분리하고, 차단은 IsControlEnabled 단일 게이트로 통합했습니다. 이후 게임패드 등 다른 디바이스 추가도 에셋 수정만으로 가능해졌습니다.
